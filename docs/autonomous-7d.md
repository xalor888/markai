### 第 9 批（D5 质量 · 删假检测）— 2026-11-02

**16. 「后台异常退出 N 次」是死代码**（0.2.44）

  **证伪**：把 dead key 加回去 → 守卫立刻点名。
- 教训：**"看起来在工作"比"明显没工作"更危险**——它会让后续判断都建立在假的信号上。

### 第 7 批（D1 稳定性 · 严重的自审发现）— 2026-11-02

**14. 撤销点校验白名单漏了 `moveBatch` / `delete`，会删掉用户的撤销历史**（0.2.42）

- 真实 kind 是 `create / delete / move / moveBatch / update`，
  而健康检查与修复器各写的 `isUsableUndoPoint` 只认 `move / update / create`
  （外加两个根本不存在的 `remove` / `sort`）。
- **后果不是漏报**：`dropCorruptUndo` 按这份判断**直接删点** →
  含批量移动或删除的撤销点被当"损坏"清掉 →「刚删了一批书签，怎么撤不回去了」。
- 0.2.37–0.2.41 期间点过「修复全部」的用户可能已中招。书签本身没动，丢的是撤销能力。
- 修：抽出 `src/lib/undo/validate.ts` 作唯一来源 + **编译期守卫**
  `AssertSame<UndoOp['kind'], KnownOpKind>`——以后加 kind 忘了加白名单，tsc 直接失败。
- 回归 T108 六条；**证伪两次**（改回白名单→红；只改运行时集合→另一条红）。

**教训**：这是"同一个判断写两遍"的典型代价。
自己新写的模块也要当陌生代码审——上一轮审出草稿丢字，这一轮审出删数据。

### 第 5 批（D1 稳定性 · 自审）— 2026-11-02

**10. 收尾时丢掉最后 300ms 的生成文本**（commit `092a899`）— **我自己上一版引入的**
