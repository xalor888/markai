# 错误处理约定与"静默失败"清扫清单

这个项目的判定标准很朴素：**不要把失败呈现成正常**。这份文档记录两件事：
(1) 遇到错误时该上报还是可以忽略的规则；(2) 一次实际清扫的结果（修了什么、还剩什么）。

## 1. 规则：什么时候必须如实上报

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| **写用户可见状态失败**（书签操作、设置、对话、撤销记录） | **必须上报**，且要带上可核对的细节（真实占用、原因）与可操作建议 | UI 已经显示成"成功"，静默失败就是假话；用户会在下一次启动/下一次操作时才发现，且无法归因 |
| **安全相关字段保存失败**（如删除模式 `deleteMode`） | **必须上报并点名风险** | "改为需要确认"若没落盘，重载后 Agent 会不打招呼就删——用户以为自己受保护 |
| 读操作失败但**降级为空**（如 `chrome.bookmarks.get(id).catch(() => [])`） | 视语义而定：若"不存在"与"读失败"在该上下文等价（例如删除时目标已消失也算达成），可忽略；若会把"读失败"显示成"没有数据" | 前者是刻意的语义（已在删除执行器里注释），后者是假话（会把"查不到"说成"没有"） |
| 纯装饰性/尽力而为的写入（主题、剪贴板、格式化、右键菜单重复注册兜底） | 可以忽略 | 失败不影响用户对数据状态的判断；上报只会变成噪音 |
| 清理/收尾类操作（`storage.remove`、定时器清理） | 视情况而定，**必须先确认它不会毁掉唯一副本** | 撤销的 pending 快照就是"清掉就没了"的唯一副本：早期实现在正式点写入成功**之前**就删它，写失败时改动彻底不可撤销（已修）。**重复提升也不是无害的**——删除类逆操作会重复重建子树，所以恢复按事务身份去重 |

新增代码请按此表判断，并在忽略处写一句话说明**为什么不影响判断**（空 catch 不带理由是不允许的）。

## 2. 已修掉的静默失败（每处都有可失败的测试）

| 位置 | 症状 | 修法 |
| --- | --- | --- |
| `undo/recorder.writeUndoPoints` | 超配额导致撤销点丢失，界面显示"没有可撤销的操作" | 容量护栏（4 MiB）+ 丢弃如实说明 + 失败上报，见 DIRECTION §4A |
| `aiStore._persist` | 对话写盘失败被空 catch 吞掉，界面照常显示历史 | 6 MiB 预算 + 常驻警示条 + `getBytesInUse` 真实占用 |
| `configStore.update` | 设置（含 **API Key** 与 **删除模式**）保存失败被空 catch 吞掉，UI 已显示新值 | 如实上报 + 设置页可见警示（删除模式额外点名安全风险）+ 重试入口 |
| `undo` 被中断的轮次 | Service Worker 被杀时已完成的改动没有任何撤销点 | 增量落盘 + 启动恢复（见 DIRECTION §4A） |
| `undo` 正式点与 pending 的**交接** | 收尾/恢复先删 pending 再写正式点：写失败时唯一快照已被删，改动彻底不可撤销（且恢复仍返回"成功"） | 正式点**写成功后才清 pending**；写失败则保留并补全 pending、返回 null；恢复按 `runId` 去重，避免"清了 pending 失败"变成两个可回放点（`undo/recorder.ts`，T37 七条用例 + 三条反证） |
| `undo` 消费失败可**重复回放** | `takeUndoPoint` 忽略消费写入失败，`applyUndo` 仍可能报成功；原点留在存储里，再点一次会重复执行——删除类逆操作会重复重建子树 | `takeUndoPoint` 如实回报 `removed`；消费失败**先自动重试一次**，仍失败则返回 `ok:false` 并明确警告"不要重复点击"；同一 SW 会话内记住已执行过的点并拒绝重复应用（`undo/apply.ts`，T38 七条用例 + 四条反证）。**残留风险**：跨会话（SW 重启）后这道内存保护会消失，届时重复点击仍可能重复执行——已如实标注，未修复 |
| 已消费的点被残留 pending 复活 | 去重只扫描当前 points：点被**消费**后 runId 随之消失，若 pending 清理失败且进程又被杀，下次启动会把它提升成**新 id 的可执行点**——删除类逆操作可被重复回放 | `markai.undo` 增加有界 `terminalRunIds`；`takeUndoPoint` 把移除与记账放在同一次写入（原子）；恢复前先查终态，已终结者只清 pending 不生成新点（T47 七条 + 两条反证） |
| 重叠的并发撤销回放 | `appliedThisSession` 只在「回放结束且消费失败」之后登记，挡不住重叠请求：两次 `applyUndo(同一点)` 各自读到同一目标、各自通过检查，删除类逆操作会把同一棵子树**重建两份** | 在全部只读检查之后、任何副作用之前建立进程内 `inFlight` 集合，检查与登记之间无 await（单线程下原子）；T46 用可控 create 闸门确定性构造重叠（T46 六条 + 反证）。**跨进程未覆盖**：SW 回收后集合消失 |
| 消费失败却显示「已撤销」 | `applyUndo` 消费写失败返回 `{ok:false, restored>0, failures:[]}`；`undoLast` 按 failures 分支判断，掉进成功 toast，忽略「不要重复点击」的告警 | `undoLast` 改为先判 `!ok`：零还原 → 「无法撤销」；已还原但记录未更新 → 「撤销未完成 + 已还原 N 项 + 原因」（T45） |
| 读取撤销记录失败被当成「没有记录」 | `refreshUndo` 的 catch 把列表清空，界面于是断言「没有可撤销的操作」——把不确定说成确定 | 新增 `undoUnknown` 标记；读取失败/形状异常时置位，面板显示「撤销记录读取失败，当前状态未知」，成功读取时清除（T45） |
| 删除预扫描把读取失败说成「书签已不存在」 | `chrome.bookmarks.get(id).catch(() => [])` 把**读取失败**与「节点确实不存在」混为一谈，于是瞬时读取失败被 `count++` 计成**删除成功**——用户以为删掉了、其实还在 | 区分两者：读取抛错 → 如实报「无法确认该书签的状态（读取失败）」；确实不存在 → 维持「目标已达成」（避免 UI 卡在可重试的 pending）。T50 + 反证 |
| 复制书签后改名失败被吞掉 | `jUpdate(created,{title}).catch(() => {})` 吞掉失败后仍回报请求的标题，模型与用户都以为改名成功 | 副本照常建出（不抹掉已完成的事实），但按实际标题回报并标 `renamed:false` + `note`（T50 + 反证） |
| 主题保存失败静默丢弃 | `themeStore.setTheme` 的 catch 为空：主题当次生效但没落盘，重启后「自己变回去了」，与设置页（`configStore` 有警示）口径不一致 | 本次切换照常生效，同时弹 destructive「主题设置没有保存成功」并说明重启后可能回退（T51 + 反证） |
| 快捷键打开侧边栏失败静默 | Ctrl+Shift+M 的 `sidePanel.open` 失败是空 catch——**按了没反应** | 复用「不依赖 storage 的工具栏提示」通路（抽出可测的 `lib/ai/toolbar-hint.ts`），并让右键指令失败提示与它共用同一实现（T52 + 反证） |
| 批量移动把「部分完成」说成「整体失败」 | `bookmark-tree` 拖入文件夹与 `bookmark-list` 拖放用顺序 `await` 循环 +一句笼统的「移动失败」：第 3 项抛错时前 2 项**已经移过去了**却不说，用户不知道到底动了几项；同一功能的另外两处（`move-picker`、"移动到其他根文件夹"）却用 `allSettled` 如实报计数——两种口径并存 | 抽出 `src/lib/bookmarks/bulk.ts`：`moveMany` 逐项独立计数（含首个失败原因）、`describeBulk` 统一话术（全成功 success / 部分成功「已移动 X 项，Y 项失败」/ 全失败「移动失败」/ 空输入不谎报），四处调用点统一走它（T49 十条 + 源码守卫；两条反证） |
| 打开链接失败完全不可见 | UI 里近二十处 `void chrome.tabs.create({...}).catch(() => {})`：在书签树按回车、点「打开全部」失败时**没有任何反应**；批量路径还会**无条件**弹「已打开 N 个标签页」，把可能一个都没打开说成成功 | 统一走 `src/lib/open-url.ts`：`openUrl` 失败弹 destructive；`openUrls` 按**实际**结果报「已打开 X 个，Y 个失败」/「打开失败」，全成功才 success；提示只显示 URL 来源（origin），不泄漏路径与查询参数；弹窗补挂 `ToastViewport` 并改为「打开成功才关弹窗」（T48 十一条 + 源码守卫 + 两条反证） |
| 撤销新建文件夹会连带删除后来内容 | `applyOne` 的文件夹 `create` 逆操作是 `removeTree`（无条件递归）：若该文件夹在本轮**之外**被放入内容（手工/另一窗口/未记账的移动），撤销会连内容一起删，而本轮快照里没有它们——不可恢复 | 回放前新增**只读预检** `findFolderRemovalConflicts()`：列出文件夹现存子项，排除「本点自己的 `create` 会删掉」与「本点的 `move`/`moveBatch` 会移回原处（`fromParentId !== 该文件夹`）」两类，剩余即冲突 → 零副作用拒绝并**保留**撤销点，提示用户先移走内容；`applyOne` 同时改为非递归 `remove` 作纵深防御（T43 九条；反证回滚预检必须变红） |
| 撤销历史「跳选较早点」 | `applyUndo(id)` 接受任意仍在列表中的点，只逆转该点自己的操作却不回退更晚的点；而"撤销新建文件夹"是 `removeTree` 无条件递归 → 「A 新建 F、B 把已有 X 移入 F、跳选撤 A」会连 X 一起删，且 A 的快照里没有 X | `applyUndo` 只接受当前 `points[0]`：非最新点在任何 `chrome.bookmarks.*`、顺序还原与 `takeUndoPoint` 之前零副作用拒绝并保留点；历史面板如实禁用较早记录并给出「请先撤销较新的操作」（T42 八条；反证回滚该检查必须变红） |
| `background` 右键指令 seed 写失败 | `.catch(() => {})` 吞掉写入失败后照样打开侧边栏并广播 → 用户只看到**空聊天**，不知道指令没保存；完整页 `tabs.create` 失败也被静默忽略 | 抽出可测的 `src/lib/ai/context-menu.ts`：写失败时**不打开、不广播**，改用**不依赖 storage 的工具栏提示**（badge + `action.setTitle`）说清失败；完整页打开失败同样给可见反馈；成功路径清掉历史提示（T40 八条用例 + 三条反证） |
| 「清空本地数据」漏清 pending | 只删 `markai.undo`，进行中的快照可能在下次启动被恢复成一个"用户以为已清掉"的撤销点 | `clearUndoPoints()` 一并清除 `markai.undo.pending`（T38）。**边界**：它无法取消正在运行中的轮次——那一轮结束仍会写下新撤销点，这是刻意语义而非静默失败 |
| `undo` **pending 写入竞态** | 写入 fire-and-forget、完成顺序可能与发起顺序不一致（慢的旧写入最后落地 = 快照回退）；收尾/清空只删一次键，一条在路上的写入会在清理之后把它复活 | 写入走**串行链**（落盘顺序 = 发起顺序）；收尾/清空**先等在途写入全部落定再删键**（`drainPendingWrites`），因此不存在"清理之后才落地的写入"——连"进程恰好在此刻被杀"的窗口也一并关掉（`undo/recorder.ts`，T39 五条用例 + 三条反证）。**跨进程边界**：恢复那侧仍靠 `runId` 去重兜底 |

## 3. 仍未处理的（四个高风险类别已逐项判定，但全量枚举仍未逐处审计）

下面先给出原先四条"按类别判定"的高风险类别的**逐项结论**，再列出**仍然没有逐处复核的部分**——
这份文档不声称这些 catch 都被逐处看过。

逐项结论（证据行号为判定时的实际位置）：

1. **`background.ts` 右键指令路径 — 已修**（见 §2 与 T40）。判定过程读到的同文件其余 `catch`：
   - `recoverInterruptedTransaction()` 的 `void ...`（启动恢复）：失败由该函数内部按 `writeUndoPoints`
     结果与 `lastWriteError` 上报，不是吞错；
   - `applyUndo` 抛错时的 `sendResponse({ok:false,...})`：把异常如实回给调用方，属正确；
   - 徽标清理 / 无监听者时的 `sendMessage` / `contextMenus` 重复注册兜底：**按 §1 规则属可忽略**
     （纯装饰或幂等重试，失败不改变用户可见状态），理由已在 §1 给出，不再算"未复核"。
2. **`tools.ts` 并发池与重试 — 已逐个核对，无遗留静默失败**：
   - `checkUrls`（并发 5）与 `checkUrlsBulk`（并发 20）与 `cleanupSweep` 的存活检测（并发 20）：
     每条结果都写进 `results[i]` 的**逐条状态记录**（`status: 'ok'|'dead'|'skipped'`），
     不存在"某条失败但整体报成功"；
   - `autoCategorize` 的 move 池：worker 抛错会让 `Promise.all` reject，外层 `catch` 以
     「分类执行中断：…（已创建 N 个文件夹，已移动 M 条书签）」抛出，**如实带出已完成量**；
   - `cleanupSweep` 的删除池：`retryDelete` 返回布尔，成功 `autoDeleted++` / 失败 `autoFailed++`，
     两者都进结果 JSON（`deleted` / `failed`）与摘要文案；
   - `open_bookmarks` / `merge_folders` 的虚报已由既有反证守护（见 §4 的反证清单）。
   结论：没有需要新修的项，因此**本项无代码改动**。
3. **打开动作失败不可见 — 已修**（本次）：原先 UI 里有近二十处
   `void chrome.tabs.create({...}).catch(() => {})`，点了没反应；批量路径更会**无条件**弹
   「已打开 N 个标签页」。现在统一走 `src/lib/open-url.ts`：`openUrl`（单个，失败弹 destructive）
   与 `openUrls`（批量，按**实际**结果报「已打开 X 个，Y 个失败」/「打开失败」，全成功才 success）；
   提示只显示 URL 的**来源**（origin），不把完整 URL（可能含 token/查询参数）打进 UI。
   弹窗（`popup/main.tsx`）原先**没有挂 toast 视口**，那里的提示同样看不见——已挂载 `ToastViewport`，
   并改为"打开成功才关弹窗"。守卫：T48 十一条断言 + 一条**源码守卫**（UI 里不得再出现
   `tabs.create` 与 `.catch(() => {})` 同行）+ 两条行为级反证。
4. **`apply.ts` 撤销逐条失败 — 已确认 UI 必展示**：`undo:apply:result` 的消费方只有
   `aiStore.undoLast` 一处（`background.ts` 只做转发）；它在 `!ok` 与 `ok` 两个分支里都检查
   `failures.length > 0` 并弹出明细，因此不存在"收集了 failures 但没人显示"的路径。
   契约由 T24（部分失败明细）与 T45（消费写失败走 `!ok` 分支）固定，**本项无代码改动**。
   唯一残留：`failures.length === 0 && !ok && restored > 0` 这一类已由 `!ok` 优先分支覆盖；
   真正未覆盖的是"非空的 failures 数组里某些条目被详情截断"这种展示层细节，未做限制。

## 4. 怎么验证这些结论不是嘴上说说

- 每条修复都配了"回滚实现 → 对应测试必须变红"的反证用例（`node scripts/falsify.mjs`，当前 115 条，真实 exit=0 才算通过）；
