# 错误处理约定与"静默失败"清扫清单

这个项目的判定标准很朴素：**不要把失败呈现成正常**。这份文档记录两件事：
(1) 遇到错误时该上报还是可以忽略的规则；(2) 一次实际清扫的结果（修了什么、还剩什么）。

## 1. 规则：什么时候必须如实上报

| 情形 | 处理 | 理由 |
| --- | --- | --- |
| **写用户可见状态失败**（书签操作、设置、对话、撤销记录） | **必须上报**，且要带上可核对的细节（真实占用、原因）与可操作建议 | UI 已经显示成"成功"，静默失败就是假话；用户会在下一次启动/下一次操作时才发现，且无法归因 |
| **安全相关字段保存失败**（如删除模式 `deleteMode`） | **必须上报并点名风险** | "改为需要确认"若没落盘，重载后 Agent 会不打招呼就删——用户以为自己受保护 |
| 读操作失败但**降级为空**（如 `chrome.bookmarks.get(id).catch(() => [])`） | 视语义而定：若"不存在"与"读失败"在该上下文等价（例如删除时目标已消失也算达成），可忽略；若会把"读失败"显示成"没有数据" | 前者是刻意的语义（已在删除执行器里注释），后者是假话（会把"查不到"说成"没有"） |
| 纯装饰性/尽力而为的写入（主题、剪贴板、格式化、右键菜单重复注册兜底） | 可以忽略 | 失败不影响用户对数据状态的判断；上报只会变成噪音 |
| 清理/收尾类操作（`storage.remove`、定时器清理） | 视情况而定，**必须先确认它不会毁掉唯一副本** | 撤销的 pending 快照就是"清掉就没了"的唯一副本：早期实现在正式点写入成功**之前**就删它，写失败时改动彻底不可撤销（已修）。**重复提升也不是无害的**——删除类逆操作会重复重建子树，所以恢复按事务身份去重 |

新增代码请按此表判断，并在忽略处写一句话说明**为什么不影响判断**（空 catch 不带理由是不允许的）。

## 2. 已修掉的静默失败（每处都有可失败的测试）

| 位置 | 症状 | 修法 |
| --- | --- | --- |
| `undo/recorder.writeUndoPoints` | 超配额导致撤销点丢失，界面显示"没有可撤销的操作" | 容量护栏（4 MiB）+ 丢弃如实说明 + 失败上报，见 DIRECTION §4A |
| `aiStore._persist` | 对话写盘失败被空 catch 吞掉，界面照常显示历史 | 6 MiB 预算 + 常驻警示条 + `getBytesInUse` 真实占用 |
| `configStore.update` | 设置（含 **API Key** 与 **删除模式**）保存失败被空 catch 吞掉，UI 已显示新值 | 如实上报 + 设置页可见警示（删除模式额外点名安全风险）+ 重试入口 |
| `undo` 被中断的轮次 | Service Worker 被杀时已完成的改动没有任何撤销点 | 增量落盘 + 启动恢复（见 DIRECTION §4A） |
| `undo` 正式点与 pending 的**交接** | 收尾/恢复先删 pending 再写正式点：写失败时唯一快照已被删，改动彻底不可撤销（且恢复仍返回"成功"） | 正式点**写成功后才清 pending**；写失败则保留并补全 pending、返回 null；恢复按 `runId` 去重，避免"清了 pending 失败"变成两个可回放点（`undo/recorder.ts`，T37 七条用例 + 三条反证） |
| `undo` 消费失败可**重复回放** | `takeUndoPoint` 忽略消费写入失败，`applyUndo` 仍可能报成功；原点留在存储里，再点一次会重复执行——删除类逆操作会重复重建子树 | `takeUndoPoint` 如实回报 `removed`；消费失败**先自动重试一次**，仍失败则返回 `ok:false` 并明确警告"不要重复点击"；同一 SW 会话内记住已执行过的点并拒绝重复应用（`undo/apply.ts`，T38 七条用例 + 四条反证）。**残留风险**：跨会话（SW 重启）后这道内存保护会消失，届时重复点击仍可能重复执行——已如实标注，未修复 |
| 「清空本地数据」漏清 pending | 只删 `markai.undo`，进行中的快照可能在下次启动被恢复成一个"用户以为已清掉"的撤销点 | `clearUndoPoints()` 一并清除 `markai.undo.pending`（T38）。**边界**：它无法取消正在运行中的轮次——那一轮结束仍会写下新撤销点，这是刻意语义而非静默失败 |
| `undo` **pending 写入竞态** | 写入 fire-and-forget、完成顺序可能与发起顺序不一致（慢的旧写入最后落地 = 快照回退）；收尾/清空只删一次键，一条在路上的写入会在清理之后把它复活 | 写入走**串行链**（落盘顺序 = 发起顺序）；收尾/清空**先等在途写入全部落定再删键**（`drainPendingWrites`），因此不存在"清理之后才落地的写入"——连"进程恰好在此刻被杀"的窗口也一并关掉（`undo/recorder.ts`，T39 五条用例 + 三条反证）。**跨进程边界**：恢复那侧仍靠 `runId` 去重兜底 |

## 3. 仍未处理的（如实列出，别当成已经清完）

一次全量枚举（`src/` 全目录，含 tools.ts）：**`catch {` 共 64 处**、**`.catch(() => …)` 共 84 处**。
它们**并非都是问题**——按上表，多数属于"合理忽略"（读取缺失节点、UI 装饰写入、清理收尾）。
但这份清单目前是**按类别**判定过的，**不是逐处审计过的**：下面是已知还需要逐个看的高风险类别：

1. `background.ts` 中的消息回退路径——已确认右键指令的 seed 写入失败会继续打开侧边栏（用户可能只看到空聊天）；另有完整页 `tabs.create` 失败无反馈。尚未修复；
2. `tools.ts` 里的并发池与重试（单个失败被计为 failed 是刻意的，但需确认所有失败都会汇总进结果）；
3. `bookmark-tree.tsx` / `bookmark-list.tsx` 的拖拽与打开动作（`chrome.tabs.create` 失败目前不可见）；
4. `apply.ts` 撤销回放中的逐条失败（已收集为 failures，但需要确认 UI 一定会展示非空 failures）。

**撤销这条主线**：容量护栏、被中断轮次的恢复、持久化交接、消费失败、清空漏清 pending、
**pending 写入竞态**均已修复（见 §2）。**仍未修复**的是上面第 1 条（background 右键指令的 seed 写失败）。
撤销这侧保留的**跨进程残留边界**：迟到写入的补偿依赖进程内的纪元计数，SW 被杀时补偿不会执行——
那条路径由恢复时的 `runId` 去重兜底（不会造出重复点，但"已消费的点被迟到快照复活"仍需真机量化）。

把这些逐个判定并给出结论，是这份文档的**下一步**。

## 4. 怎么验证这些结论不是嘴上说说

- 每条修复都配了"回滚实现 → 对应测试必须变红"的反证用例（`node scripts/falsify.mjs`，当前 82 条，真实 exit=0 才算通过）；
- 反证脚本会**响亮失败**在三种情况下：测试是假绿、回滚后仍然全绿、锚点失效（SKIP）——它抓出过本项目自己写的多处测试缺陷；
- 涉及真实 API 语义的地方（`getBytesInUse`、`chrome.storage` 结构化克隆、`bookmarks.move` 下标）都以实测或权威源码为准，替身按同样语义建模。
