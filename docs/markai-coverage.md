# MarkAI 改动覆盖清单（断言 vs 只靠眼睛）

> 为什么需要这份表：第 15 轮发现「设置页直达按钮」在文档里标了完成、代码里却从未存在——
> 那次改动用的字符串替换没匹配上，静默失败了。这类「文档撒谎」只有**可执行的断言**能防住。
>
> 用法：改动任何一项能力前先看这里有没有对应断言；没有的话，改完就该补一条。
> 单测 = `tests/agent.test.ts`；e2e = `scripts/e2e-smoke.mjs`；截图 = `scripts/visual-audit.mjs`。

## 三、跑一次要多久

`node scripts/e2e-smoke.mjs`（**97 项**，本机实测）：

- 稳定性：2026-11-01 四道门全绿；本轮新增「补整理规模数字与实际一致」等断言（96 → 97 项）。
  大改动后建议连跑 3 次——flaky 的测试比没有测试更糟：它会训练人忽略红灯。
- 完整档：**约 125s**（2026-11-01 实测 121.5s）
- 快速档 `MARKAI_E2E_QUICK=1`（跳过 大库渲染 / 新用户视角 / 补整理的取消，少 7 条断言）：约 115s
- **快速档只省几秒**——因为耗时分散在几十个小 `setTimeout` 上，不是集中在某几段。
  它现在的价值是「少跑 7 条与本次改动无关的断言」，不是「快很多」。若真要大幅提速，
  得把各处固定 `sleep` 逐个换成条件轮询，那是另一项工作。


| 分段 | 耗时 |
| --- | --- |
| 时间线 | 1.5s |
| 长消息 | 3.0s |
| 删除与待删清单 | 0.6s |
| 自动整理 / 分页 / 树定位 | 9.2s |

> 这份表在 2026-10-26 做过一次**对齐修正**：此前 `markSection` 的位置全部错在段落**结尾**，
> 于是每个数字实际量的是"下一段"，一直把「整理记录 43s」当成大头——真正的大头是
> **「快捷键/大库/多选」41.8s**（里面含 1200 条大库渲染）。

大头是「补整理」相关——那里真的造了 400 条书签、跑到一半取消、再清理干净。
这部分耗时是**测量本身的价值**（取消必须验在中途），不该为了跑得快而砍掉。
固定 sleep 已换成条件轮询（`waitFor`），省下的不多但慢机器上更稳。

## 四、曾经是局限、**仍然存在**的（不要被「已解决」误导）

| 局限 | 现在的状态 |
| --- | --- |
| 补整理 N 条 → N 个撤销点，上限 10 会把它们挤掉，「补整理 200 条后想整体反悔」只能退最近 10 步 | **仍然是 N 个点，没有合并。** 「整批合并成一个撤销点」试过、技术上也能合并，但撤销这个点时「新建文件夹」是**递归删除**，会连带删掉同批已移入的内容，后面的 move 回放找不到目标（实测 124 条只 restored 5）。**可靠性优先，方案已回退**，改为提供「撤销全部 N 步」缓解连点疲劳。见 `src/entrypoints/background.ts` 的 `runOrganizeSweep` 注释与 `e2e`「现状记录：补整理后撤销点被上限截断」 |

## 五、用户可见文案的用词（T96 守卫）

同一个概念只用一种说法，`src/components` 与 `src/entrypoints` 里禁止出现别名：

| 概念 | 用 | 不用 |
| --- | --- | --- |
| 功能名 | 自动整理 | 自动分类 |
| 用户动作 | 撤销 | 撤回 |

内部注释、给模型的 prompt、日志 id 不受此限（那不是用户看的字）。

**指南也必须用同一套词**（T97）：`docs/user-guide.md` 里出现界面上不存在的说法（例如「免打扰」）就报错——
用户拿着指南在对不上的界面里找，是最容易放弃的时刻。
