## 二、「识别新书签并自动整理」做成了什么

原来是「后台静默归位 + 一条会消失的 toast」。现在是一条**完整闭环**，而且**有记性**。

### 1. 三层决策（先便宜后聪明）

新增 `src/lib/ai/organize-rules.ts`：

| 分数 | 依据 | 是否直接采纳 |
| --- | --- | --- |
| 100 | 文件夹名 = 站点品牌（`GitHub` ← github.com） | ✅ 直接采纳，**省一次模型调用** |
| 80 | 文件夹名包含品牌（`我的 GitHub 收藏`） | 交给模型确认 |
| 70 | 文件夹名 = 站点语义类别（`开发` ← github.com） | 交给模型确认 |
| 60 | 文件夹名包含语义类别（`前端开发`） | 仅在模型不可用时采纳 |
| — | 低于 60 / 超过 3 层 / 根自身 / 短品牌（`x`） | 不参与 |

约束都有测试兜着：短品牌不误伤（`x.com` 不得命中「Excel 笔记」）、深分类不插手、
同分取更浅层（候选顺序变了结论也不变）。

### 2. 每一次自动整理都留痕

`src/lib/ai/organize-log.ts`：环形缓冲 200 条落 `chrome.storage.local`，
**并发写入串行化**（多条书签同时整理完成时，「读-改-写」并发会互相覆盖丢记录，有专门用例）。
每条记录：标题 / 域名 / 动作 / **去了哪个文件夹** / 一句人话原因 / 是否失败 / 是否可重试 / **撤销点 runId**。

### 3. 整理记录面板

- 顶栏「整理」入口，失败时挂红点；`#organize` 深链；popup 有「今天已整理 N 条」摘要
- 统计：今天 / 累计 / 失败；一行「归到：设计资料 3 · 自动整理/github.com 1」看出东西都塞哪儿了
- 逐条去向；**最新一条淡高亮**；支持按标题/域名/去向**检索**，可叠加「只看失败」
- 成功的 → **一步撤销**（书签回原处，临时建的站点文件夹一并回收）
- 失败的 → **重试**（成功后就地变绿，不再一红一绿）
- 顶部 → **补整理已有书签**：只处理散落在根目录的，你手搭的分类不动；带进度（显示当前条目）、可取消、45 秒无进度会如实收尾

### 4. 有记性：撤销即免打扰

用户在整理记录里点「↶」说的是「这个站点这么归类我不认」。现在：
- 该**注册域**进入免打扰名单，之后**新收藏不再自动搬**；
- **手动「补整理」仍会处理**（用户主动要求时必须真的执行）；
- 名单在面板底部可见，**每个站点可单独恢复**，也可全部恢复。

### 4.5 整理记录：一处「能带走」的透明度

面板上有一行 **判断来源：本地规则 N · 模型 N · 兜底 N**（也写进导出文件）。
它回答的是用户会问但以前查不到的问题——**AI 到底用了多频繁**。本地规则命中越多 = 越快也越省钱。

### 4.8 性能回归（2026-10-26 复测）

| 规模 | 补整理耗时 | 主线程 |
| --- | --- | --- |
| 1000 条 | **5.0s**（5.0ms/条） | 最长一帧 20ms，无超过 100ms 的帧 |
| 10000 条 | **15.1s**（1.5ms/条） | 最长一帧 **38ms**，**0 帧**超过 100ms |

12000 条规模下补整理从最初的 402 秒降到 20 秒级。
1 万条时曾出现 245ms～1.3s 的主线程长帧，已定位并修掉：补整理持续产生 `onMoved` 事件，
固定 300ms 去抖意味着整场要跑约 66 次全树刷新（每次 = getTree + 一万节点重渲染）。
改成**连续变更时退避到 1.2 秒**后：最长帧 **1346ms → 38ms**、超 100ms 的帧 **14 → 0**，
总耗时也从 20.3s 降到 **15.1s**。

### 5. 批量补整理能跑得动

导入几百条书签后点「补整理」，原先每条独立决策：同域名重复问模型、某域名超时后其余条目还各等一次 12 秒。现在：
- **同域名复用结论**（`moveBookmarkInto`，仍走撤销事务）
- **失败域名降级**（`skipAi`，单测断言**零请求**）
- e2e 断言同域名两条补整理后落在**同一个文件夹**

### 6. 可配置

「允许 AI 参与自动分类」关掉后**一次请求都不发**（用完整配置 + 请求计数验证），仍走本地规则与域名兜底。

> 修掉一个隐蔽缺陷：`resolveConfig` 是**字段白名单**，新字段不加进去会被静默丢弃——
> UI 存进去了、后台读出来还是默认值，设置「看起来生效了但没生效」。

### 三·1 可访问性（实测，不是目测）

用 WCAG 公式遍历每个文本节点算 contrast ratio，**10 种状态全部 0 处低于 AA**：
主界面浅/深、320px+深色、320px+深色+对话框、对话框打开后、toast 显示时、深色下 toast、
空状态、弹出窗、设置页、侧边栏。

过程中**修掉一处真问题**：深色下 `--color-accent: #6366f1` 作为**文字色**对比度只有约 4.0:1
（`AI` 3.91、`书签栏` 3.11）。提亮到 `#818cf8` 并配套把 accent 块上的文字改成深色 `#10131a`。

## 四、只有肉眼/实测才能发现的问题（值得单独记）

1. **安装时自动打开设置页会让工作区卡 20 秒**。Chrome 扩展的 options / sidepanel / page / popup
   **共享同一个渲染进程**，900 行设置表单的初始化会和工作区抢主线程；现象是大库下时间线从 19ms 变成 20 秒不响应。
   已撤掉该行为，并在代码里写清原因。
2. **错误边界不能用 `flex-1` 包装层**——会破坏子元素高度约束（同上，时间线 20 秒不响应）。改用 `display: contents`。
3. **免打扰跳过被当成「自动整理未完成」弹红警告**——用户自己关的站点，每次收藏都报警只会把提示当广告。
   改为静默但**留痕**（写日志，不弹 toast）。
4. **`?` 快捷键在事件靶点不是元素时静默失效**（`closest` 不存在导致处理函数抛错）。

## 五、性能实测（不是估的）

- 数据层（5000 条）：展平 / 排序 / 分组 / 过滤各步 < 400ms，单测设了防退化护栏（T82）
- 渲染层（**1200 条真实书签**）：时间线首屏 **16–30ms / 80 行**，已进 e2e 固定检查
- 批量写入（`scripts/stress-sweep.mjs`，独立临时 profile，不碰真实书签）：

  | 规模 | 优化前 | 优化后 |
  | --- | --- | --- |
  | 3000 条 | 35.1s（11.7ms/条） | **5.0s（1.7ms/条）** |
  | 10000 条 | 402.5s（49.3ms/条） | **25.1s（2.5ms/条）** |
  | 12000 条 | 未测 | **25.3s（2.1ms/条）** |

  根因是 O(n²)：每条移动都要 `getChildren(根目录)` 拿「移动前下标」，1 万条在根目录时
  等于每条读 1 万项并线性查找。改成由调用方维护一份父目录顺序（首次 `getChildren` 一次，
  之后本地同步），把 IPC 从 1 万次降到 1 次。正确性另有 T91 守着（撤销要靠这个下标回原位）。

> 压测当场抓到一个真问题：补整理**只处理了 200 条就停了**（`collectLooseBookmarks` 的上限），
> 剩下 400 条静静躺在根目录且**没有任何提示**。已改为自动分批：处理完一批就按当前树重新扫，
> 直到根目录没有可收的书签；失败过的条目记进 `processed` 集合，不会被反复捞起死循环。

## 七、怎么自己验一遍

```bash
cd /Users/xalor/Documents/markai
npx tsc --noEmit && npx tsx tests/agent.test.ts && npm run build && node scripts/e2e-smoke.mjs
node scripts/visual-audit.mjs          # 15 张截图 → .output/visual/
```

手工验收自动整理：

1. 打开侧边栏，收藏一个网页（`Cmd+D`）；
2. 一两秒后应出现「已自动整理新书签」toast，书签落到合适的文件夹（**第一次**会多一句「之后可在顶栏『整理』里回看与撤销」）；
3. 点顶栏「整理」→ 看到这条记录、它去了哪、为什么；点「↶」→ 书签回到原处，**同时该站点进入免打扰**；
4. 面板底部能看到「已停用自动整理：xxx」，可单独或全部恢复；
5. 点「开始」（补整理）→ 散落在根目录的书签被收走，随时可「取消」。
