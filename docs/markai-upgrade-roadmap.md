## 1. 问题清单（全部来自实拍截图与代码，不是猜的）

### A. 空间与布局

- **A1｜设置页内容列过窄**：1180px 窗口里内容卡片只有约 440px，左右各空 370px；表单纵向拉得很长（单个 AI 服务卡片近 900px 高）。证据：`06-options.png`。
- **A2｜中栏宽屏浪费**：1440px 下时间线/列表行内容只占左半边，右侧整片空白；「已显示全部 N 条」居中在容器里显得偏右。证据：`02-full-light-timeline.png`。
- **A3｜紧凑侧边栏两栏都挤**：430px 下左树固定 176px，中栏只剩 254px，工具栏（全部/整理/搜索框）挤成一团。证据：`04-sidepanel.png`。

### B. 反馈与空状态

- **B1｜根目录只有文件夹时中栏一片空白**：没有「这里只有文件夹，选一个看看」之类的引导。证据：`01-full-light-list.png`。
- **B2｜书签图标加载失败无占位**：离线/favicon 取不到时行首是空洞（截图里所有行都没有图标）。证据：`02-full-light-timeline.png`。
- **B3｜弹出窗两个实心主按钮打架**：「去配置」与「打开完整管理页」同为 accent 实心，视觉上没有主次。证据：`05-popup.png`。
- **B4｜弹出窗缺「刚刚发生了什么」**：自动整理是后台行为，popup 是用户最容易看到它的地方，却只显示待删与最近动态。

### C. 新书签自动整理（用户点名的功能）

- **C1｜只能靠 `onCreated` 触发**：用户已有的书签没有「补整理」批量入口，只能开 Agent 对话。
- **C2｜结果不可回看**：整理成功只发一条 toast，错过就没了；没有整理日志/统计，用户无法知道「它到底动了什么」。
- **C3｜AI 未配置时一律 `自动整理/<域名>`**：会把书签栏变成几十个单域名文件夹。缺少本地规则（已存在文件夹的语义匹配、常见站点归并、同域合并到已有分类）。
- **C4｜失败无重试**：AI 超时/报错直接落兜底，用户不知道可以重试，也没有「稍后再试」。
- **C5｜批量风暴直接放弃**：导入/同步时整轮跳过并冷却 60s，但没有在界面留下降级说明或「补整理」入口。

### D. 人性化与操作

- **D1｜危险操作确认文案不统一**：删除确认、清空会话、撤销历史里的措辞风格各异。
- **D2｜快捷键只存在于 README**：界面内没有可发现的快捷键提示（除 popup 底部一句）。
- **D3｜空状态缺少「下一步动作」**：部分空状态只有说明文字，没有可点按钮。
- **D4｜动效只有 150ms 淡入**：树展开/折叠、列表行变化、时间线切组没有空间连续性。

## 2. 分批计划（按用户点名的顺序排优先级）

### 阶段一 · 自动整理闭环（C1–C5）
1. 本地规则引擎 `src/lib/ai/organize-rules.ts`：域名→分类名映射、同域归并、已有文件夹名模糊匹配（纯函数 + 单测）。
2. 整理日志 `src/lib/ai/organize-log.ts`：环形缓冲（最近 200 条）落 `chrome.storage.local`，含时间/标题/结果/目标路径/是否可撤销。
3. 「补整理已有书签」批量入口：扫描根目录下的散落书签（不在任何分类里的），逐条走同一套决策，带进度与取消。
4. 失败重试：把可重试的失败（超时/网络）记入日志并暴露「重试」。
5. 批量风暴不放弃：风暴结束后提示「检测到 N 条导入，点这里补整理」。

### 阶段二 · UI 空间与布局（A1–A3、B1–B3）
6. 设置页：内容列放宽 + 分区导航（左侧锚点列表），表单改为两列栅格。
7. 中栏：内容限宽居中（列表/时间线统一），宽屏不再左倾。
8. 紧凑侧边栏：树可折叠成图标条 / 一键收起，窄屏优先中栏。
9. 空状态统一组件：图标 + 一句说明 + 一个主操作。
10. Favicon 占位：取不到时显示域名首字母色块。
11. Popup：主次按钮分层 + 增加「最近自动整理」摘要。

### 阶段三 · 人性化（D1–D4、B4）
12. 危险操作文案统一 + 二次确认组件。
13. 快捷键帮助浮层（`?` 打开）。
14. 空状态补动作按钮。
15. 动效：树折叠、行插入/移除、视图切换的空间连续性（遵守 `prefers-reduced-motion`）。

### 阶段四 · 收口
16. 全量回归（四道门 + 视觉截图 6 张 + 对比）。
17. `docs/markai-upgrade-report.md` 交付报告：逐项「问题→改法→验证证据」。

### §8 第 2 轮补充：错误边界与一次「改对了又撤掉」

- **渲染错误边界**（`components/common/error-boundary.tsx`）：原先任何组件抛错都会让整棵树卸载 →
  **纯白窗口**、无提示、无退出路径。现在中栏/Agent 面板/各入口各有边界，出错显示一句人话 +
  具体错误 + **重试**按钮 + 可展开的组件栈。
  - 关键实现细节：正常渲染时用 `display: contents` **不产生盒子**——第一版用了 `flex-1` 包装层，
    直接破坏中栏的高度约束，时间线在 1200 条时从 19ms 变成 20 秒不响应（e2e 稳定复现）。
- **撤销的 UI 路径有了 e2e**：点整理记录里的「↶」→ 消息 → background → applyUndo → 树刷新，
  真实浏览器断言「书签从 `16` 回到 `1`」。
- **一次撤回的改动（附原因）**：曾加「首次安装自动打开设置页」。实测发现 Chrome 扩展的
  options / sidepanel / page / popup **共享同一个渲染进程**——900 行设置表单的初始化会和工作区抢主线程，
  症状是大库下时间线 20 秒不响应。已撤掉，并在代码里写明原因；「不知道去哪配置」改由
  popup 未配置提示 + 聊天欢迎卡片 + 设置页「三步开始用」三处覆盖。

### §9.5 第 3 轮追加：可访问性 + 「有记性的自动整理」

- **站点免打扰（新能力）**：用户在整理记录里点「↶ 撤销」= 明确否定了这个站点的归类方式。

  整理记录加 `role="list"/"listitem"` 与列表名；状态图标标 `aria-hidden`（语义由文案承载，避免重复朗读）。

### §17 第 9 轮（✅ 完成 —— 本轮有真成果，也有一次自我纠正）

**成果：批量补整理去掉 O(n²)，1 万条从 402 秒降到 25 秒。**

| 规模 | 优化前 | 优化后 |
| --- | --- | --- |
| 3000 条 | 35.1s / 11.7ms 每条 | **5.0s / 1.7ms** |
| 10000 条 | 402.5s / 49.3ms 每条 | **25.1s / 2.5ms** |
| 12000 条 | 未测 | **25.3s / 2.1ms** |

根因：`jMove` 每条都要 `getChildren(根目录)` 取「移动前下标」，1 万条在根目录 = 每条读 1 万项 + 线性查找
→ O(n²)。改成由调用方维护父目录顺序（首次一次 `getChildren`，之后本地同步），IPC 从 1 万次降到 1 次。
**正确性另有 T91 守着**（撤销靠这个下标回原位，拿错就会悄悄打乱顺序）。

**一次自我纠正（重要）**：中途我测到「优化后反而更慢」，于是回滚了 batching / 进度节流 / undo 去抖三处改动，
并写下「优化无效」的结论。继续查下去发现真因是**测试环境被污染**——反复压测留下 11 个 Chrome 进程 + 62 个临时 profile，
互相抢 CPU，让同样的代码凭空慢 3 倍（清理后完全回到 35.1s 基线）。
- 已给三个测试脚本都加上 profile 清理，避免再犯；
- 那三处回滚仍然保留（在干净环境里它们听不出差别，少一层复杂度更好），但**结论改成「收益未证明」而不是「有害」**。

**方法论教训**：性能结论必须先证明环境干净。这轮的 402s → 25s 是在同一次干净环境里前后对比测出来的，才可信。

### §43 第 35 轮（⚠️ 尝试后撤回 · 一次诚实的技术结论）

**目标**：让一次补整理共用一个撤销点，解决「补整理 200 条只能退 10 步」。

**做法**：sweep 外层按 200 条 `beginUndoTransaction()`，内部每条靠 `isRecording()` 复用。

**结果：没生效，已整段撤回。** 实测 120 条补整理后仍是 10 个点、每点 1 op，
且每个点的 runId 是 `auto-organize:<书签id>` —— 不是我设的 `auto-organize:sweep:<ts>`，
说明调用链里的 `isRecording()` 读到的是 **false**，批量事务根本没被感知。根因没查清。

**为什么撤回而不是留着**：半生效的分支比不修更糟——它会让下一个读代码的人以为做过。
代码里留了完整说明（试过什么、观察到什么、下次先做哪一步诊断）。

**把测试改成「记录现状」**：e2e 里那条用例现在断言的是「10 个点、各 1 op」，
标题直接写「已知局限：…」。它**不谎报缺陷已解决**，同时把 runIds 摊出来，方便将来修这块时看格式。

### §44 第 36 轮（✅ 上一轮的失败修好了 —— 「先证明再改」奏效）
