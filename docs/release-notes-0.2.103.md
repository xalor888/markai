# v0.2.103 — 「清理整理记录」这个按钮，有时点了没用

## 缺陷

`storage.near-quota`（本地存储已用 X MB）的修复动作是「清理最占空间的整理记录」。

但**存储不止整理记录一块**：撤销点（含被删书签的子树快照）、对话历史都算在内。

占用来自别处时，用户点了修复 → 日志清到 200 条以内 → 占用还是超阈值 →
**问题原样还在、健康分不动**。用户看到的就是「点了没反应」。

这正是 0.2.68 那一类：**修复按钮修不好它声称的问题**。

## 修法

快照新增 `logBytes`（单独量整理记录的占用）。诊断据此决定：

- 日志**至少占总占用一成** → 提供修复（清它真的可能把总量拉到阈值以下）
- 否则 → **不提供修复按钮**，并在 `manualHint` 里说清真正的占用在哪
  （「主要占用在撤销记录与对话历史里」）

给一个点了没用的按钮，比不给按钮更糟——它让用户以为自己在解决问题。

## 验证

两面都验：

```
A. 日志占 8/9 MB → 有修复按钮，修完问题消失
B. 日志只占 4 KB → 没有修复按钮，且提示指向真正的占用
```

**证伪**：把条件改回无条件提供 → B 面立刻红：
`不该提供「清理整理记录」——那是一个点了没反应的按钮`。

## 顺带修了一个我自己造成的测试基础设施问题

前几轮追加的契约测试都写在主 IIFE **外面**，而且是 `void okA(...)`（不等待）——
它们一直在**并发**跑，既竞争共享的 `storageMap`，「全部通过」那行也可能在它们跑完之前就打印。

已全部移进 IIFE 并改成 `await okA(...)`。移进来之后立刻暴露了两处被掩盖的污染。
