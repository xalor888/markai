# v0.2.108 — 撤销的最棘组合：删 + 移 + 建混在一轮

## 缺口

撤销系统里最难的一条路径，是**三种操作混在同一轮**：

| 操作 | 撤销时要做什么 | 坑 |
|---|---|---|
| `delete` | 按快照**重建**子树 | 重建出来是**新 id** |
| `move` | 还原到源父目录 | 下标要按 Chromium「移除前坐标」换算 |
| `create` | 删掉 | — |

而顺序检查点里存的是**动手前的旧 id**，必须靠 idMap 翻译成重建后的新 id——
否则顺序还原会静默错位：**树"看起来对"，但兄弟顺序变了**。

以前只分别测过：纯删除、纯并发删除、删文件夹带子树。**没有这条混合路径。**

## 补上了

```
PASS  同一轮里删除 + 移动 + 新建混着来，撤销后该子树（含顺序）复原
```

构造：父目录 `[a, b, c, d]` → 删 `b`、把 `d` 搬到别处、新建一条 →
撤销 → 断言该子树的内容与顺序回到 `[a, b, c, d]`，且搬走的那条真的回来。

## 断言为什么只覆盖自己的子树

bookmark store 是**模块级共享数组**，跨用例累积且不重置。第一版比整棵树，
被别处的状态干扰（实测：撤销后根目录多出一个「前端」文件夹）。

操作集合也只校验**落在自己节点上**的那几条——recorder 的 `active` 事务同样是模块级状态，
别处迟到的写入可能落进同一轮（实测有个迟到的 `jCreate` 混进来），**不替它背书**。

## 验证

证伪：让 `create` 的逆操作不删除 → 套件转红，断言正是「撤销后必须与操作前完全一致」。

（诚实说明：套件在第一条失败即中止，所以转红的是相邻一条同样守该不变量的用例；
本条用例的断言在逻辑上同样敏感——`T28-new` 若没被删掉，子树比对立刻不等。）
