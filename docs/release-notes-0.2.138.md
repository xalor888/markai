# v0.2.138 — 上一轮公布的数字是错的，这轮改正

## 我上一轮说错了什么

0.2.137 公布：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 一次性渲染行数 | 6,182 | 800 |
| 耗时 | **721ms** | **336ms** |

**那两个耗时数字里塞进了测量伪影。**

计时循环长这样：

```js
for (let i = 0; i < 40; i++) {
  await sleep(150);                                    // ← 每轮睡 150ms
  const n = await ev(`document.querySelectorAll(...).length`);
  if (n === rows && n > 0) break;
  rows = n;
}
const elapsed = Date.now() - t0;                       // ← 把睡眠也算进去了
```

行数要过好几轮才稳定，于是 300–600ms 的轮询睡眠被算进了"渲染耗时"。

## 改成精确计时后的真实数字

改用 `waitFor` 只等"到达"，耗时单独算：

| | 无上限 | 有 800 上限 |
|---|---|---|
| **树（6182 行）** | **233ms** | **39ms** |

**约 6 倍差距——收益是真的**，只是没有我说的那么夸张（233→39，不是 721→336）。

## 顺带撤掉一个没有收益的改动

顺着这个思路我去查了**中栏列表**（同样没有渲染上限），加了同样的 500 行帽。

测下来：

| | 无上限 | 有 500 上限 |
|---|---|---|
| **列表（3000 行）** | 29ms | 1ms |

**差异在噪声范围内**（React 提交是异步的，两帧后才落到 DOM）。而 `getChildren` 取 3000 条只要 21ms，两帧内就完成了——**列表根本不慢**。

所以这个改动**没有真收益**，已撤回。留下它只会让人以为"这里也优化过了"。

## 教训

"应该更快了"必须附改前改后的数字——**而数字本身要先证明不是伪影**。
一个带 `sleep` 轮询的计时循环，测出来的是睡眠时长，不是被测代码。
