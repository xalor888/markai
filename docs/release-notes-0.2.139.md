# v0.2.139 — 节流落盘：撤销时可能少还原几条

## 缺陷

pending 快照是节流的（`PENDING_MAX_LAG_OPS=5` / `PENDING_THROTTLE_MS=250`）：既已作用到书签上的操作，可能还不在 pending 里。

如果进程在**节流窗口内被杀**——那几个操已经生效了，但撤销点里没有。恢复后拿到的撤销点**少于实际改动**，撤销它**撤不干净**。而 `applyUndo` 无从知道少了几条，仍会返回 `ok: true`。

实测（6 条删除，不等节流窗口就杀进程）：

- 实际删除 **6** 条
- 撤销点只记了 **5** 条
- 撤销后只回来 **5/6** 条
- `applyUndo` 仍报 ok：**「已成功撤销」但有一条永远回不来**

## 修法

把告知补上：**诚实说明可能少记了几个操作**。

```ts
const lagNote = `；快照是节流落盘的，最后最多 ${PENDING_MAX_LAG_OPS} 个操作可能没有被记录，撤销时可能少还原几条`;
```

同时把节流阈值从 5 降到 2，缩小窗口但不能消除——所以必须诚实说清楚。

## 验证

新增一项单元测试（单测 851→852）：断言恢复提示必须包含这两段话

```
PASS 节流窗口内被杀：撤销点会少记已生效的操作（不能假装撤干净）
  [DBG] 实际删除 6 条，撤销点记了 5 条
  [DBG] 残余风险：撤销报 ok=true，只回来 5/6 条
```

日志如实记录了这条无法消除的残余风险。

**证伪**：去掉告知 → 断言转红，失败信息正是我们想避免的用户误读（「报成功但没撤干净」）。

## 教训

有些残余风险消不掉（要消掉就得每个操作都同步落盘，5000 条的整理会被拖垮），
所以只能**如实说**——让用户知道"我看到的提示可能不完整"。
