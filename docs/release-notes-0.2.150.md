# v0.2.150 — 最彻底的中断，反而没被标成中断

## 缺陷

0.2.145 加了 `UndoPoint.interrupted`，让撤销历史能区分「完整做完的一步」和「取消掉的半步」。
但撤销点有**两条产生路径**，当时只接了一条：

| 产生路径 | 场景 | 0.2.149 之前 |
|---|---|---|
| `endUndoTransaction({interrupted: signal.aborted})` | 用户点「停止」 | ✅ 已标记 |
| `recoverInterruptedTransaction()` | **SW 被浏览器回收**，启动时把死进程留下的 pending 提升成撤销点 | ❌ **没标记** |

第二条是**最彻底的中断**——整轮被浏览器掐断，比用户手动取消更该被标出来。
但它在撤销历史里显示的是一条普通记录：

```
删除 2 项        ← 进程被杀后恢复的，看起来和做完的一模一样
```

用户分不清它是做完的还是断掉的。

## 修法

`recoverInterruptedTransaction` 构造点时直接 `interrupted: true`——pending 只可能来自
已经死掉的进程，所以恢复出来的点**必然**是被中断的那一轮。

## 验证

新增 1 项单测（865 → **866**）：真的造一个 pending、`dropActiveForTest()` 模拟进程被杀、
恢复、再走 `describeUndoHistory` 看摘要。

**证伪**（注释掉 `interrupted: true`）→ 转红：

```
[DBG] 恢复出的撤销点摘要: 删除 2 项
✘ 进程被杀后恢复出来的撤销点也要标「已中断」
❌ ...实际：删除 2 项
```

修复后：

```
[DBG] 恢复出的撤销点摘要: 删除 2 项（已中断）
```
