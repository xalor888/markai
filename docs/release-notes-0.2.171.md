# v0.2.171 — 概览不再显示已删书签 · 整理落位补齐

## 一、已删除的书签仍出现在概览

### 现象

删掉一条书签后，打开「概览」仍能在「最近整理」里看到它。
用户会合理地以为删除没生效，或这条书签还留在库里。

### 根因

概览的「最近整理」直接摊开 `markai.organize.log` 最近五条。
这份日志是**只增不减的历史**：书签被删除时，日志不会跟着清理。
所以记录本身没错，错的是概览把它当成了"当前库里的书签"。
指标（总数 / 重复 / 空文件夹）来自当前书签树，本来就会随删除更新；
只有这一块把历史记录和现存状态混在了一起。

### 修法

- 新增纯函数 `filterDeletedOrganizeEntries(entries, roots)`（`src/lib/ai/organize-log.ts`）：
  - 有 `runId = auto-organize:<bookmarkId>` 的记录：按**书签 id 是否还在树上**判断（移动、改名都不会误删记录）；
  - 早期没有 `runId` 的记录：按归一化 URL 是否仍在库里判断（同一 URL 还有其他副本时保留）；
  - 没有 URL 的系统记录（如「批量新增 N 条」的跳过摘要）保留。
- 概览只渲染过滤后的记录；完整历史仍留在「整理记录」里。
- 树还在加载时不过滤：空 `roots` 会被误当成"书签都删了"，导致刚打开就显示空记录。

## 二、整理"选择存放位置"只做了一半

### 已补完的部分

**1. 任意落点，不再只有"原文件夹 / 书签栏"**

「整理方案等待你确认」卡片新增「其他文件夹」：带搜索的文件夹列表，
可以选「其他书签 / 工作」这类任意目标。暂存区内部与批次自己的子树不可选；
`applyBatch` 也会在底层拒绝循环嵌套。原文件夹被删后，卡片会禁用「应用到原文件夹」，
但仍可换落点或放弃（放弃回落到书签栏）。

**2. 四个整理入口统一口径，且真正跟随设置**

`lib/ai/organize-prompt.ts` 成为唯一指令来源：聊天起手 chip、书签树右键、
列表工具栏、`/整理` 斜杠命令全部走它。设置 `organizeStaging` 关闭时，
四处都会改成"直接建在目标文件夹内部"，不会一边说关了、一边要求先开批次。
普通聊天里直接说"帮我整理某文件夹"也不会绕过设置：`agent.ts` 按设置把
【整理落位策略】注入系统提示，`stage_organize` 工具在关闭时硬拒绝。

**3. 暂存区不再可能接管用户自己的同名文件夹**

早期 `findStagingRoot` 按标题「自动整理」认领，用户自己建一个同名文件夹就会被混用，
变空后甚至可能被删掉。现在元信息里保存**我们创建的根 id**，只认这个 id；
标题兜底仅用于旧元信息的升级迁移（已有批次、且批次父级同名），不会凭"看起来像"接管。

**4. 同名不同文件夹不再并批，落位失败不再留下幽灵**

- 两个不同文件夹恰好同名时各开一批，批次标题补「书签栏 / 其他书签」或数字后缀，
  避免应用 A 的批次时把分类搬进 B；
- 批次内直接子项移动中途失败时保留批次记录，用户可重试；只有壳真的空了才删除，
  不会出现"文件夹还在、元信息没了"的孤儿；
- 用户手动删掉批次节点后，待确认列表与顶栏计数会自己归零。

**5. 待确认方案不再藏在菜单深处**

有暂存批次时：顶栏出现「待确认整理 N」入口，「更多 → 整理记录」带数量角标，
概览的「管家建议」也会排在最前面提示去确认。点进去就是可应用/换落点/放弃的卡片。

## 四、影响

- 概览的含义更准确：统计与「最近整理」都只反映当前仍存在的书签；历史仍在整理记录中。
- 默认行为改为"先暂存、再落位"。已经习惯直接整理的人可以在设置页关掉暂存，恢复旧行为。
- 旧版本留下的暂存根/批次元信息会按 id 或旧批次父级迁移，不会清空用户书签。
