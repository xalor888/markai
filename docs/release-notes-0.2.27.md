# MarkAI v0.2.27 发布说明

## 概述

v0.2.27 是对 Agent 链路的一次**针对性重构**：把「动不动就断流」「模型适配很垃圾」
这两类反馈拆成具体的根因逐条修掉，而不是重写整个 Agent。

改了四件事：模型上下文窗口真正按模型生效；SSE 解析抽成可单测的纯模块并修掉三个
解析缺陷；超时模型从"一个总超时盖全程"改为"首字节 + 空闲"的活动式看门狗；
流被截断时整轮重发，且重发前通知 UI 作废旧文本。

## 一、模型适配：`getModelContextWindow()` 此前是死代码

`src/lib/providers.ts` 里有一张 30 条的模型→上下文窗口表，但**生产代码里没有任何一处
调用它**，只有测试在用。实际生效的是一条写死的 `DEFAULT_CONTEXT_WINDOW = 1M`：

| 模型 | 真实窗口 | v0.2.26 及更早实际给的值 | 超配 |
|---|---|---|---|
| `deepseek-v4-flash` | 128K | 1,048,576 | **8×** |
| `qwen3:8b`（Ollama） | 128K | 1,048,576 | **8×** |
| `kimi-k3` | 256K | 1,048,576 | 4× |
| `gpt-5.1-mini` | 400K | 1,048,576 | 3× |

后果：上下文护栏的预算被抬到 **832,799 token**（1M × 0.8 − 固定开销 6,062），
等于**永不触发**——请求一路堆到超出模型真实窗口，被服务端 400 或截断。
而超预算时的提示还写着"可在设置页调大模型上下文长度"，方向是反的。

**修法**

- 新增 `effectiveContextWindow(model, saved)`：显式配置优先，**否则跟随模型**；
  不再有任何"统一 1M"的兜底（未知模型按 128K 取——给小了最多是提前压缩，给大了会直接撑爆）。
- **旧配置迁移**：靠新增的 `configVersion` 识别。v0.2.26 及更早存下来的配置没有这个字段，
  其中的 `contextWindow` 一律视为"非用户意图"（那时根本没别的值可写）并丢弃，改用模型窗口。
  不用"是否等于 1M"来判断——那会误伤真的手动填了大窗口的用户。
- `applyPreset()` 切换服务商/模型时清空 `contextWindow`，避免旧值跟着新模型走。
- 设置页：展示"当前跟随模型 → 128K"，手动改过之后出现「跟随模型」按钮可一键还原；
  超预算提示改为"调低自动压缩阈值 / 开启自动压缩 / 换更大窗口的模型"。

## 二、SSE 解析抽成纯模块 `src/lib/ai/stream.ts`

原来这段逻辑埋在 `fetch` 读循环里，只能靠 mock 整条流来测——于是"流被中途截断"
这种真实场景**从来没被构造过**（替身总是吐完整的流）。抽成纯函数后可直接喂字节、逐条断言。

顺带修掉三个解析缺陷：

1. **一行脏数据会吃掉紧随其后的有效行**。旧写法直接把"上一行残留 + 当前行"拼起来解析，
   于是前一个坏行与后一个合法 JSON 拼在一起必然失败，**一次丢两行**。
   改为先试当前行本身、失败才拼接——合法行直接生效，垃圾单独告警丢弃。
2. **不记录 `[DONE]` / `finish_reason`**。认得 `[DONE]` 但只是 `return`，没有任何地方记录它，
   读循环结束也不检查。流被掐断时无从判断。现在 `completed = sawDone || finishReason !== null`。
3. **末尾残留的半截行没有判据**。新增 `pendingTail`：连一行都没发完就断开的情况可被识别。

另外 `finish_reason === 'length'`（输出被 max_tokens 截断）现在会如实告警，
不再把一段没说完的话当成完整回答。

## 三、流被截断 = 失败并重发（此前会把半截参数当成真工具调用）

**旧行为**：流中途断了 → 半截的 tool_call arguments 照样被拼出来，当成一个真实工具调用发出去
→ `executeTool` 的 `JSON.parse` 抛错 → 连续两轮失败 → "工具执行连续失败，请换个说法重试"。
用户看到的就是 agent 莫名报错、不知道在做什么。

**新判定**（两个条件同时成立才算传输中断，缺一不可）：

- 没收到 `[DONE]` / `finish_reason`；**且**
- 工具调用参数是半截 JSON，或末尾残留了解析不出来的半截行。

只按"没收到 [DONE]"判会误杀——不少兼容端点不发 [DONE] 也不带 finish_reason；
只按"参数不是合法 JSON"判也不行——那是模型自己的输出问题，交给执行器报错即可，
重试 5 次只会白烧请求。

## 四、重发前通知 UI 作废旧文本（新增 `chat:restart`）

此前 `client.ts` 里有一句 `if (hasOutput || …) throw e`：**只要已吐出过一个字，
任何失败都不再重试**——为的是避免两段回复拼在一起。代价就是"回复中途断流 = 整轮硬失败"。

现在改成：可重试的错误一律重试，重试前若已投递过内容就回调 `onRestart`，
后台向 UI 发新的 `chat:restart` 事件，UI 清空该消息后重新接收。
`src/stores/aiStore.ts` 已实现对应处理（含丢弃 16ms 批次里未落盘的残文）。

## 五、超时模型：从一个总超时改为活动式看门狗

| | v0.2.26 及更早 | v0.2.27 |
|---|---|---|
| 模型 | `REQUEST_TIMEOUT = 120s` 覆盖**请求 + 整个流式读取** | 首字节 120s + 空闲 60s，**每收到数据就重置** |
| 长回复 | 生成得慢但一直在出字也会被掐断 | 只要持续有数据就一直进行 |
| 推理模型 | 首 token >120s → abort → 重试 5×120s ≈ **10 分钟无响应** | 首字节 120s 内判断一次，超时即如实报错 |
| 连接挂死 | 干等满 120s | 60s 无新数据即判定中断 |

## 测试与反证

- 全量自动化测试：**493 项全绿**（482 → 493，新增 T71 十一条：
  分片拼接 / [DONE] 与 finish_reason / 缺结束信号仍返回内容 / 半截参数 / 末尾半截行 /
  脏数据不吃掉有效行 / 跨行 JSON 拼回 / **截断后整轮重发** / **重发前回调 onRestart** /
  超时模型的静态锚点）。
- T15 里那条 `resolveConfig(...).contextWindow === 1_048_576` 的断言是本轮失效设计的
  直接证据，已改为断言"跟随模型 = 128K"，并补了一条迁移守卫。
- 行为级反证：共 **169 条**（165 → 169）。本版发布前对新增的 4 条做了定向实跑，
  **全部 `RED ✔`**。全量仍未跑完（一条 ≈ 17 秒，169 条约 48 分钟），如实记录，不当成已解决。
- 门禁：`npm run compile` ✔ / `npm test` 493 全绿 ✔ / `npm run build` ✔（858.62 kB）。

## 升级建议与已知事项

- **建议升级**。本次改的是"请求为什么会失败/被截断"的根因，不是体验微调。
- **配置迁移会自动发生**：升级后首次打开设置页（或任意一次保存）时，旧的 1M 会被丢弃、
  改为跟随模型。若你确实需要覆盖（例如走的是带更大窗口的中转），在设置页手填即可。
- **未做**：模型能力检测（不支持 tool calling 的模型没有降级路径）——31 个工具、
  约 5K token 的 schema 仍无条件随每个请求发出。小尺寸本地模型若表现异常，
  这一条仍是缺口，不在本轮范围内。
- **真机验证仍是空白**：证据是「替身测试 + 定向反证 + 对 Chrome/HTTP 行为的文档核实」，
  不构成在真实浏览器与真实服务商上的行为证明（P3）。
- 产物资产只有 **chrome zip**（MV3，Chrome/Edge 手动加载）；不产出 Firefox 产物——
  它从未在真实 Firefox 里装过一次，按本项目「不发没人验证过的产物」的标准不该发布。
