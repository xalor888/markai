# v0.2.39 — 切个标签页，回复不会再没了

## 你补的那句信息是关键

> 我只是把标签页放后台罢了，切个标签页就没。

上一版我按"关闭页面"来修（落盘 + pagehide），方向就偏了。真相是：

```
切到后台 → 页面定时器被 Chrome 节流到 ~1 次/分钟
         → 20s 一次的保活心跳失效
         → Service Worker 30s 空闲被回收
         → port 断开
         → background 里 port.onDisconnect 直接 abort()   ← 生成被当场杀掉
```

**内容不是丢了，是生成被中止了。** 而且 UI 那边的 `streaming` 被置为 false，
切回来时 `visibilitychange` 触发的 `load()` 不再被守卫拦住，又用 storage 里的旧内容
覆盖了内存里更完整的那份。

三处一起修：

## 1. 端口断开不再立刻中止（`background.ts`）

给 30 秒宽限期：期间这一轮跑完，内容会落进会话消息，你切回来直接看到完整回复；
确实没人回来，才中止以免白烧 token。新一轮开始时清掉上一轮的倒计时，
避免它到点把新的请求杀掉。

## 2. 后台自己写草稿（`lib/ai/stream-draft.ts`）

每个增量在 background 累积成草稿，每 300ms 落盘一次。
**不再依赖 UI 的定时器**——坏掉的恰恰是"UI 还活着"这个前提
（后台标签页的定时器会被节流到分钟级）。

## 3. 收尾必须落成消息，而不是只删草稿

`finalizeDraft()`：一轮结束时把草稿的最终文本写进**会话消息**（UI 下次 `load` 真正读的地方），
然后把 `streaming` 收尾、清掉草稿。只删不写的话，port 早断、UI 一直没回来的那种情况，
内容就真的没了。

## 4. 合并只往更完整的方向走

`mergeDraft()` 的规则只有一条：**草稿更长才采用**。
晚到的一次读绝不会把你眼前的字变少；重试造成的分叉也不会拼成两段怪回复（取更长的那份）。

## 回归

新增 T104 / T105 共 8 条：

- 草稿累积与节流落盘、切到新消息时重新开始
- `mergeDraft` 只往长方向合 / 分叉不拼接
- 一轮结束草稿被清
- **端到端**：storage 是旧快照 + 草稿更完整 → `load()` 后消息被补全
- `finalizeDraft` 把草稿落成会话消息、幂等、无草稿时不改写存储
