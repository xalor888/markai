# v0.2.42 — 修一个会**删掉你撤销历史**的 bug

## 先说严重性

0.2.37 上线的「健康检查」，其中「清理损坏的撤销点」这一项有个判断错误：

它认得的撤销操作只有 `move / update / create`，
**漏掉了 `moveBatch`（批量移动）和 `delete`（删除）**。

这两个恰好是最需要撤销的两类操作。

后果不是「漏报一次」，而是：

1. 健康检查会把含它们的撤销点报成「N 个撤销点已损坏」；
2. 如果你点了「修复全部」，`dropCorruptUndo` 会按这个错误判断**直接把点删掉**；
3. 于是「我明明刚删了一批书签，怎么撤不回去了」。

**如果你在 0.2.37–0.2.41 之间点过「修复全部」，含批量移动或删除的撤销点可能已经被清掉。**
书签本身没动（修复从不碰书签），丢的是"还能不能撤回"这件事。

## 根因

两处各写了一份 `isUsableUndoPoint`（健康检查一份、修复器一份），
两份的 kind 白名单都是错的，而且实现还不一样——典型的"同一个判断写两遍"。

## 修法

抽出 `src/lib/undo/validate.ts` 作为唯一来源，并且加了一道**编译期守卫**：

```ts
type AssertSame<A, B> = [A] extends [B] ? ([B] extends [A] ? true : never) : never;
const _kindListMatchesType: AssertSame<UndoOp['kind'], KnownOpKind> = true;
```

以后给 `UndoOp` 加一个新的 kind 而忘了加进白名单，**tsc 直接编译失败**，
不会再等到线上把用户数据删掉才发现。

## 回归

T108 六条：

- 白名单必须覆盖真实 kind；
- 含 `moveBatch` 的点必须被认作完整；
- 含 `delete` 的点必须被认作完整；
- **真正损坏的点仍然被认出来**（不是把校验改成永远通过）；
- 修复器只删真正损坏的那一条，三个好点（move / moveBatch / delete）一个都不能少；
- 诊断不会把它们报成「已损坏」。

证伪做了两次，分别单独验证：
- 把白名单改回错误版本 → 「覆盖全部 kind」转红；
- 只把运行时判断改错、保留常量 → 「含 moveBatch 必须被认作完整」转红。

## 你现在该做什么

1. 升级到 0.2.42；
2. 打开设置页看健康检查——如果之前被误报，这条错误现在会消失；
3. 如果之前点过「修复全部」且确实丢了撤销点：**那些点已经找不回来了**（当时被真的删掉了）。
   书签本身完好，从现在开始不会再发生。
