# v0.2.52 — 给「唯一不可逆的操作」补上浏览器级验证

## 为什么是删除

删除是整个产品里唯一**不可逆**的动作，安全设计的核心是：

> AI 只能提交提议 → 用户显式点击 → background 才真正 `removeTree`

这条链路以前只有单测。这一版用假 AI 服务让模型真的发出 `propose_deletions`，
在浏览器里跑完整条路径。

## 四条断言

1. 模型提议后，界面上出现待删条目
2. **没点确认之前，书签一条都不能删** ← 安全底线
3. 待删条目上有可点的删除按钮
4. 用户点了之后，书签真的被删掉

## 过程中抓到的两个我自己的问题

### 一、段落之间互相污染

第一次跑出现 59/61（两条与本段无关的检查失败），重跑又全绿——**测试不稳定**。

根因是几个 AI 段落共享同一条聊天状态，前一段留下的对话会影响后一段。
现在每个 AI 段落起跑前先清 `markai.ai`，做到互不影响。之后连跑 7 次全绿。

### 二、安全断言没有灵敏度

我把 `proposeDeletions` 改成「无视确认模式直接删」，模拟一个严重回归。

结果：**「没点确认之前不能删」依然是绿的。**

原因是断言只查了 `chrome.bookmarks.get(id).length === 1`，
而那次错误实现删掉的时机/对象让这条查询返回了 1（另有一条检查因为卡片消失而转红，
说明产品确实是坏的——但我的安全断言没抓到）。

改成同时查「按 id」和「按 url」，并先静置 1 秒（否则测的是"删得够不够快"）：

```
FAIL  · {"byId":0,"byUrl":1,"victimId":"12"}
```

这次真的红了。两个方向都验过：正确代码 PASS，直接删 FAIL。

## 又一次同样的教训

这是七天内**第三次**「断言通过了，但它测的不是它声称的东西」。

前两次是拿长度当判据、拿空会话当判据，这次是拿单个 id 查询当"没被删"的证据。

规则再强化一条：

> 安全类断言必须**故意破坏一次**，确认它真的会红；
> 只跑通不破坏的断言，等于没写。
