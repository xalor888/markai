# v0.2.59 — 根因在更下面一层：数据层把错误吃掉了

## 我上一版修错了地方

0.2.58 我修了「整理记录读失败时两句互相矛盾的话」。修完 e2e 是绿的。

但这一版给弹窗加同样的失败态时，e2e **直接红了**——弹窗的 `.catch` 根本不触发。

查下去发现根因在**更下面一层**：

```ts
export async function readOrganizeLog() {
  try { ... } catch { return []; }   // ← 这里
}
```

**它自己把异常吞了，返回空数组。**

于是：

- 调用方的 `.catch` 永远进不去 → 我上一版在弹窗里写的失败态**根本不可达**；
- 任何调用方都无法区分「真的没有记录」和「读不到」。

这是 0.2.55 / 0.2.57 / 0.2.58 之后的**第四次**同类问题，而且这次是在数据层，
比界面层更根本——界面层做多少判断，源头一吞就全白费。

## 修法

1. `readOrganizeLog` 不再吞错，**读失败就抛**。
2. background 的 `organize:list` 显式 try/catch，返回 `{ error }` 字段
   （而不是让整个 handler reject —— 那样发送方只会看到"通道异常"，
   分不清「读不到记录」和「联系不上后台」）。
3. 对话框见到 `error` 就提示并保留已有条目；弹窗的 `.catch` 这才真正生效。

## 验证

**T117 三条**（直接钉住根因）：

- 存储读取失败时**抛出**，而不是返回 `[]`
- 正常读取仍然返回条目（没把功能改坏）
- 没有记录时返回 `[]`（这是"真的没有"，不是"读不到"）

**e2e 两条**：打坏 `markai.organize.log` 的读取，弹窗徽标必须说「读取失败」、
正文必须说"这不代表今天没整理过"。

**证伪**：把 `catch { return [] }` 加回去 → 弹窗那两条立刻转红。

## 教训

修「界面显示错误」之前，先确认**错误有没有被传到界面**。

我在 0.2.58 修的是表现，根因在数据层。如果那边没有 e2e 逼出来，
我会以为已经修好了——而这正是"看起来在工作，其实没有"。
