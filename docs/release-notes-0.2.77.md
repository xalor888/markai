# v0.2.77 — 5000 条库的热点，实测完发现都不用优化

## 结论

台账里「5000 条库的耗时基线」这一项，实测完之后**没有需要优化的地方**。

## 数字

`node scripts/measure-biglib.mjs 5000 3`（5000 条书签 / 502 个文件夹）

| 操作 | 实测 | 说明 |
|---|---|---|
| `chrome.bookmarks.search({})` | **30ms** | Chrome 侧开销；诊断里已有 5000 条截断 |
| `flattenBookmarks`（等价遍历） | **3ms** | 时间线用，一次 O(n) 遍历 |
| `collectFolderOptions`（等价遍历） | **1ms** | 移动选择器用，同样一次遍历 |

三个都在**主线程同步跑**，也就是说书签再多也感觉不到——3ms 远低于一帧（16ms）。

## 关于「等价实现」

`flattenBookmarks` / `collectFolderOptions` 在打包产物里，页面上下文没法直接 import。
所以脚本里用的是**同等复杂度的等价实现**（都是对整棵树的一次遍历）。

这一点在脚本注释里写明了：**它测的是"这类操作的量级"，不是那两个函数的精确耗时。**
不把量级数字说成精确数字。

## 两轮实测的结论一致

| 项目 | 数字 | 结论 |
|---|---|---|
| 冷启动（450 / 1800 条） | 93ms / 144ms | 不需要优化 |
| 大库热点（5000 条） | 30 / 3 / 1ms | 不需要优化 |
| 流式落盘写入量（300 条历史） | 7 次 · 136KB | 不需要优化 |

**三轮"以为可能要优化"的地方，实测完都不用动。**

这不是浪费时间——**在动手改之前先证明不需要改**，和证明需要改同样重要。
凭感觉去"优化"一个 3ms 的函数，只会引入风险和不必要的 diff。
