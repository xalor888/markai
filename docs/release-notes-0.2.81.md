# v0.2.81 — 键盘到底能不能用书签树

## 起点：一个看着像缺陷的现象

台账里「所有可点元素可 Tab 到达」这一项。我用 CDP 扫了一遍「看起来可点但键盘到不了」的元素，
结果书签树每一行都中：

```
DIV  cursor-pointer  "书签栏"
DIV  cursor-pointer  "其他书签"
```

`<div role="treeitem">` 上挂着 `onClick`，**没有 `tabindex`**。

## 但往下查一层，发现不是缺陷

树的行确实不可单独 Tab，但**容器**是：

```tsx
<div ref={listRef} tabIndex={0} onKeyDown={onKeyDown} …>
```

方向键 / Home / End / PageUp / PageDown 都在这个容器上处理，移动的是「活动行」。

所以这是 **「一个制表位 + 方向键漫游」** 的设计——键盘用户确实能用，
和 WAI-ARIA 的 tree 模式一致。**不是缺陷，只是看起来像。**

我本来准备去给每一行加 `tabIndex`，查到这里停手了：那样会把 3000 行变成 3000 个制表位，
比现在更难用。

## 做了什么

没有改产品，加了两条 e2e 把这条键盘路径钉住：

1. 树有可聚焦的宿主（`tabindex="0"`）
2. **聚焦后按方向键，活动行会变**（不是死键）

第 2 条我第一版写松了：只断言了「聚焦成功」，而 `before`/`after` 的文本其实一模一样。
改成精确比对活动行（`[role="treeitem"].ring-1`）的文本：

```
{"focused":true,"before":"","after":"书签栏\n1","changed":true}
```

`changed: true` 是真的比到了变化。

**证伪**：去掉容器的 `tabIndex={0}` → 两条同时转红。

## 一句总结

> 扫出 6 个"键盘到不了的可点元素"，查下去发现设计本来如此。
> **这一轮的产出是"确认它不是缺陷" + 两条守卫**，不是一行产品代码。
