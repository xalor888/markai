# v0.2.83 — 「存储写满」这一项，实测后不成立

## 结论

台账里「存储写入失败（配额满）时的用户可见降级」——**不是真实风险**。

## 实测

用 `chrome.storage.local.getBytesInUse()` 在真浏览器里分键量（60 轮对话 +
200 条整理记录 + 10 个撤销点，都是按上限造满的）：

| 键 | 字节 |
|---|---|
| `markai.ai.organize-log` | 33,383 |
| `markai.ai`（对话） | 28,299 |
| `markai.undo` | 1,053 |
| **合计** | **62,735** |

配额是 `chrome.storage.local.QUOTA_BYTES = 10,485,760`（10 MiB）。

**用了 0.6%。**

## 为什么到不了

MarkAI 自己的每一项都有条数上限：

| 数据 | 上限 |
|---|---|
| 对话消息 | 60 条（`MAX_MESSAGES`） |
| 整理记录 | 200 条（`MAX_LOG_ENTRIES`） |
| 撤销点 | 10 个（`MAX_UNDO_POINTS`） |
| 流式草稿 | 单次回复长度 |

**唯一没有条数上限的是长期记忆**（`markai.memory`）——提示词注入时截 30 条，但存储不截。

按每条 300 B 算，要填满 10 MB 需要约 **35,000 条**记忆。现实中到不了。

## 做了什么

没改产品。把结论固化成 **T132 四条**，用各项上限算出**结构性上界**：

```
对话 60×2KB + 记录 200×400B + 撤销 10×2KB + 记忆 2000×300B
+ 配置 4KB + 草稿 64KB ≈ 0.85 MB  <  配额的 25%
```

四条分别是：

1. 最坏情况也远低于配额
2. **上界的构成说得出依据**（不是拍脑袋——每项都能指到具体的上限常量）
3. 记忆是唯一没有硬上限的一项，也是上界的主要来源
4. 实测数字与上界同量级（上界没有算飞）

第 2、4 条是防「为了凑一个好看的数字把上界算飞」。

**证伪**：把对话按「无上限」算 → 第 1 条立刻转红。

> 以后谁去掉某个条数上限，这条测试会立刻告诉他：**配额可能被填满了。**
