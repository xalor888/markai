# v0.2.88 — 用户最初那条抱怨，实测后不复现了

## 起点

项目最早的一条抱怨：

> 「我一旦退出，它就变成『模型未返回任何内容』」
> 「我只是把标签页放后台罢了，切个标签页就没」

当时的修法是一整套：后台草稿 + 800ms 节流落盘 + `pagehide` flush +
进程被杀后恢复。e2e 也覆盖了最狠的那种（**进程被杀后重开，内容还在**）。

但**「切到后台」这一条**从来没被单独验过。

## 实测：它不复现了

用 `chrome.storage.onChanged` 精确计时，量「内容出现在 DOM」→「进入存储」：

```
实测约 104～196ms
```

**不是代码注释里写的 800ms 节流。** 内容几乎在出现的同时就落盘了——
后台节流根本来不及吃掉它。

所以这条抱怨在当前构建里**已经不复现**。

## 做了什么

没有改产品。加了一条守卫，把这个真实保证钉住：

```
PASS  流式内容及时落盘（DOM 出现后 2s 内进入存储；实测约 104ms）
      {"saw":true,"delta":196}
```

**证伪**：去掉 delta 路径上的 `scheduleStreamPersist()` → 立刻转红。

## 过程中我写错了两次判据

### 第一次：关键词同时出现在用户消息里

我用「落盘延迟」当关键词——但它也出现在**用户消息**中。
结果 `delta: 1ms`，测到的是用户消息的落盘，根本不是流式内容。

换成只出现在模型回复里的词（「响应段落甲」）→ `delta: 196ms`。

### 第二次：等太久了，用例空转

我原本等两段内容都到齐（1.4s）再判断——而 800ms 节流在那之前就把内容写过了，
`alreadyThere` 已经是 `true`，整条用例什么都证明不了。

改成只等第一段。

## 顺带：注释与实测不符

`STREAM_PERSIST_MS = 800` 的注释说「退出时最多丢最近 800ms 的字」。
实测落盘延迟只有约 100～200ms。**注释偏保守，但方向没错**（它描述的是上限）。
没有改注释——改注释属于无产出改动，且现有描述不算错。
