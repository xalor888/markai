# v0.2.91 — 搜索用例原来是个空壳

## 缺口

搜索是**最高频的交互**。而它的 e2e 用例只有一句：

```js
check('搜索框能过滤出结果', r.ok && r.rows >= 1, …);
```

**只断言"有结果"。**

哪怕过滤完全失效、列出全部书签，它也一样绿。

## 改成什么

前后对比 + 逐行校验：

```
PASS  搜索真的过滤了（行数变少，且每一行都含关键词）
       {"allCount":5,"filtered":["Alpha 文档","Alpha-一","Alpha-四"]}
PASS  清空搜索后恢复全量列表  {"allCount":5,"restored":5}
```

- 过滤后行数必须**变少**（5 → 3）
- **每一行**都得含关键词
- 清空后必须**恢复全量**

## 过程中三个坑

### 1. 这段跑得太早，列表只有一行

实测 `allCount: 1`——行数没法"变少"，过滤就验不出东西。

在段落开头自己种了 4 条不同标题的书签。

### 2. 取标题取错了

`innerText.split('\n')[0]` 拿到的是 `"A"` / `"S"` / `"S"` 这种碎块。

原因：**搜索结果会把匹配词拆成多个 span**，innerText 就不再按行分隔。

改用行上的 `title` 属性（`标题\nURL`），split 后取第一段。

### 3. 过滤其实生效了，是我判据错

中间有一版我看到 `filtered: ["A","S","S"]` 以为过滤坏了——
其实是 5 → 3 **确实过滤成功了**，只是我取标题的方式不对。

> 又验证一次那条老规矩：**红的时候先怀疑自己的判据。**

## 验证

**证伪**：让搜索返回全部书签（不过滤）→ 我这条转红，
同时「空态『搜索无结果』带下一步」也被带红——说明空态用例一直在依赖真过滤。
